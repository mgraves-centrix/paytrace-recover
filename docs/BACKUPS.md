# Encrypted database backups

This integration includes SQLite-consistent encrypted snapshots and restore checks. The server queues a daily backup when both `BACKUP_DIR` and `BACKUP_ENCRYPTION_KEY` are configured; `npm run backup` also supports a manual run. Off-host storage and independently retained key recovery still need to be configured before a production pilot.

Set `BACKUP_ENCRYPTION_KEY` to a private base64-encoded 32-byte key. Keep the key outside Git and separate from the backup files. Set `DATABASE_PATH` to the existing PayTrace SQLite file and `BACKUP_DIR` to a private directory outside `dist`. Run `npm run backup`. The command uses SQLite's backup API, encrypts the snapshot with AES-256-GCM, checks database integrity and row counts by restoring to a temporary file, and keeps the newest seven backups by default (`BACKUP_KEEP` accepts 2–30). It prints a filename and restore result, not the key or customer data.

To test recovery, stop writes to the target environment and run `npm run restore -- <backup.pbackup> <new-database.sqlite>`. The destination must not exist. The command checks the encryption tag, SHA-256 digest, database integrity, and table counts. Inspect the new database in a separate environment before changing `DATABASE_PATH`; restoring a database does not undo an access grant already applied at an external course service.

For an independent encrypted copy, set `BACKUP_BLOB_CONTAINER_URL` server-side to a **private Azure Blob container SAS URL** with create/write permission and a rotation plan. The backup job uploads only the encrypted `.pbackup` after the local restore probe passes. A failed upload fails the job and preserves the local file for retry; backup status marks `offHost` true only after Blob returns success. Keep the SAS out of logs and Git, put the container in a separate storage account, and use its lifecycle policy for remote retention. This optional path is implemented but not configured on the public Azure demo.

For Azure App Service, store the container SAS URL as a versioned Key Vault secret and grant the app's managed identity `secrets/get`. Run `scripts/configure-azure-offsite-backup.ps1 -SubscriptionId <subscription-id> -ContainerSasSecretUri <versioned-secret-uri>`; only the Key Vault reference appears in the Azure CLI process arguments. Use `scripts/configure-azure-backups.ps1 -SubscriptionId <subscription-id> -BackupSecretUri <versioned-secret-uri>` for the encryption key. Do not rotate either secret without checking that old backups remain decryptable and the new SAS can upload. Keep a separate recovery record of the key version needed for each backup.

The backup file and encryption key must both be retained to recover. A backup stored only on the same host is vulnerable to host loss. Before release, configure the private off-host copy, store the encryption key independently (for example, a Key Vault reference), perform a restore drill from the remote copy in a separate environment, and monitor the server's daily job. An upload response is not proof that a remote restore succeeded.
